# Kafka pipeline, schema_version=1

Этот контракт добавлен для асинхронного режима Photo Advisor. Имена topics, group,
адреса и bucket заполняются в `.env`; это не существующие значения проекта.
Режим включается через `KAFKA_ENABLED=true`. Сервис не создаёт Kafka/S3.
HTTP JSON-RPC сохранён для совместимости, но для нового backend результат приходит
через Kafka. HTTP endpoint состояния объявления не добавлен.

## Вход

Kafka key: UTF-8 `listing_id`. Все события объявления публикуются с одним ключом.
Backend назначает **отдельную строго возрастающую listing_revision каждому новому
событию**, включая финализацию. Повторная доставка сохраняет event_id и все поля.
Повторное использование event_id с другим содержимым или актуальной ревизии с
другим event_id — ошибка контракта, DLQ. Пропуски ревизий допустимы.

```json
{
  "schema_version": 1,
  "event_id": "example-finalized-event",
  "correlation_id": "example-request",
  "listing_id": "12345",
  "listing_revision": 3,
  "event_type": "photoset.finalized",
  "photos": [
    {
      "photo_id": "img_001",
      "bucket": "<configured S3_BUCKET>",
      "object_key": "listings/12345/photos/1.jpg",
      "version_id": "<actual S3 version ID>"
    }
  ]
}
```

Здесь и далее значения примерные, не события и не результаты реального инференса.
В object reference внутреннее имя `photo_id` соответствует внешнему `image_id`.
Для каждого объекта обязателен непустой `version_id` и/или `etag`. VersionId
передаётся в S3 GetObject; ETag — в IfMatch. Нельзя передавать фиктивный version ID
`null`: для бакета без версионирования используйте настоящий ETag (с кавычками).
Это фиксирует содержимое, а не только изменяемый object_key. ETag не определяет
порядок событий и не трактуется как MD5.

`photoset.finalized.photos` — **полный авторитетный набор**, включая все оставшиеся
фотографии; пустой массив допустим. Backend отправляет событие после успешного
сохранения всех объектов. Сервис анализирует набор целиком, поэтому финализация
не зависит от доставки предшествующих событий отдельных фотографий.

Перед загрузкой/заменой/удалением backend публикует новое событие изменения:

```json
{
  "event_id": "example-upsert-event",
  "correlation_id": "example-request",
  "listing_id": "12345",
  "listing_revision": 1,
  "event_type": "image.upserted",
  "image_id": "img_001",
  "photo": {
    "photo_id": "img_001",
    "bucket": "<configured S3_BUCKET>",
    "object_key": "listings/12345/photos/1.jpg",
    "etag": "\"actual-etag\""
  }
}
```

```json
{
  "event_id": "example-delete-event",
  "correlation_id": "example-request",
  "listing_id": "12345",
  "listing_revision": 2,
  "event_type": "image.deleted",
  "image_id": "img_001"
}
```

Изменения дают `processing`, `missing=null`, `recognized=0`. Сервис не скачивает
фото по этим событиям: экономим CPU и не показываем окончательный чек-лист до
финализации. Сами промежуточные наборы не восстанавливаются из дельт; backend
обязан прислать полный манифест в следующей, более высокой ревизии.
Запоздавшая ревизия не меняет актуальное состояние.

Для ручной корректировки backend проверяет права пользователя и отправляет новую
финализацию с полным набором, добавляя `manual_category` к нужной ссылке на объект.
Допустимы только 12 категорий. Корректировка относится к указанной версии объекта;
при замене файла её нужно убрать. Для недоступного/повреждённого фото корректировка
не засчитывается. Для нормального файла источник результата — `manual`, confidence
равен null; это пользовательское решение, не измеренная уверенность модели.

Корректировка также не обходит качество: требуется `quality=good`. Одна группа
точных/близких дубликатов закрывает максимум одну категорию даже при разных ручных
метках. Если пригодная ручная метка есть у текущего представителя группы, он
сохраняется; иначе представителем становится первый пригодный исправленный снимок
в порядке `photo_results` (порядок входного списка). Остальные копии не засчитываются,
а `duplicate_of` указывает на выбранного представителя.

В каждой записи `photos` возвращаются дополнительные поля:

| Поле | Значение |
|---|---|
| `manual_category` | Запрошенная категория либо null |
| `manual_applied` | Засчитана ли ручная категория именно этому снимку |
| `manual_rejection_reason` | null либо `photo_error`, `quality_not_good`, `duplicate_photo` |

При отклонённой правке `source=model`, `accepted=false`; исходный `candidate`
сохраняется. Backend должен показывать причину, а не считать сам факт отправки
`manual_category` подтверждением. В очередь учебной обратной связи попадают только
применённые корректировки; это по-прежнему не разрешение на обучение.
Новые поля добавлены в `schema_version=1`: потребители должны допускать неизвестные
поля, иначе до обновления сервиса нужно обновить их строгий декодер.

Стандартные S3 ObjectCreated/ObjectRemoved JSON напрямую не принимаются. Владелец
инфраструктуры должен настроить event bridge → адаптер backend → Kafka. Адаптер
разрешает listing_id/image_id через доверенную таблицу backend или метаданные S3,
назначает ревизию и вызывает финализацию. Нельзя выводить listing_id из произвольного
ключа без согласованного контракта. Реализация такого bridge зависит от инфраструктуры
проекта и в этот этап не входит.

## Результат

Kafka key: listing_id. Пример результата только для иллюстрации схемы:

```json
{
  "schema_version": 1,
  "result_id": "<deterministic hash of listing ID and revision>",
  "event_id": "example-finalized-event",
  "correlation_id": "example-request",
  "listing_id": "12345",
  "listing_revision": 3,
  "status": "needs_review",
  "total_required": 12,
  "recognized": 0,
  "missing": ["front", "rear", "left_side", "right_side", "engine_bay", "trunk", "under_trunk", "interior", "fender_front_left", "fender_front_right", "fender_rear_left", "fender_rear_right"],
  "uncertain": ["img_001"],
  "photos": [{
    "image_id": "img_001",
    "category": "uncertain",
    "candidate": "front",
    "confidence": null,
    "similarity": 0.3,
    "accepted": false,
    "source": "model",
    "error": null
  }],
  "model": {"version": "<model revision>", "calibrated": false}
}
```

`completed` означает завершённый анализ, даже если некоторые категории отсутствуют.
`needs_review` — неопределённые/нерелевантные фото или частичные ошибки.
`failed` — все фото недоступны/повреждены либо исчерпан retry-бюджет.
После исчерпания retry missing остаётся null, чтобы не объявлять отсутствие по
неполученным данным. `uncertain` содержит image ID, `recognized` — число уникальных
подтверждённых категорий. Одна фотография закрывает максимум одну категорию.
Повторные фото одной категории не увеличивают recognized. Категории крыльев не
подменяются общим видом или диагональным ракурсом.

Backend дедуплицирует result_id, игнорирует более старые listing_revision и скрывает
старый чек-лист сразу после начала изменения набора. Рекомендации формирует своими
шаблонами. similarity — косинусная близость, не вероятность.

## Доставка, отказы и запуск

Один процесс / один Uvicorn worker / одна реплика владеет SQLite на локальном
постоянном томе. Не используйте общий SQLite через NFS и не запускайте вторую реплику
с отдельной БД в той же consumer group: это нарушит состояние после rebalance.
Для масштабирования нужно общее хранилище состояния либо partition-owned state.
Сервис теперь проверяет владение файлом через межпроцессную блокировку и отказывает
в запуске второму владельцу той же БД. Разные БД в одной группе эта блокировка не защищает.

Состояние + дедупликация + outbox фиксируются одной SQLite-транзакцией (WAL, FULL).
Outbox публикуется в Kafka, затем фиксируется offset + 1 конкретной партиции.
При аварии после публикации возможен дубль с тем же result_id. Это at-least-once,
не распределённый exactly-once. На старте сначала отправляется сохранённый outbox.
Retry-бюджет временных ошибок S3/inference сохраняется на диске между перезапусками.
Повторы обрабатываются последовательно с ограниченным экспоненциальным backoff;
это может задерживать другие объявления на одном экземпляре.

Постоянные ошибки контракта попадают в DLQ без повтора. Повреждённые/недоступные
объекты дают результат с ошибками и DLQ исходного события. DLQ содержит код ошибки,
координаты Kafka, correlation ID и исходный JSON в payload_base64, а не бинарные
фото. Вход ограничен 256 KiB; слишком большой payload в DLQ обрезается с отметкой
payload_truncated. Для повторной обработки backend создаёт новое событие с новым
event_id и большей ревизией после исправления причины.

Неисправность самой SQLite, Kafka/outbox или непредусмотренное исключение останавливает
consumer без подтверждения проблемного offset. `/health/ready` возвращает 503;
нужны оповещение и перезапуск процесса после устранения проблемы. Kubernetes/другой
оркестратор должен перезапускать зависший/неработающий экземпляр: Docker HEALTHCHECK
сам по себе контейнер не перезапускает. Незавершённый inference не отменяется при
graceful shutdown; текущий результат сохраняется, клиенты закрываются после него.

Состояние не имеет автоматического TTL: дедупликация и последние результаты растут.
Следите за диском и делайте согласованные SQLite backup. Очистку истории можно
вводить только после определения Kafka retention/replay SLA, иначе вернутся дубли.
Потеря тома требует согласованного replay входного topic, а не обычного рестарта с
уже подтверждённых offsets. Никогда не удаляйте том при обновлении контейнера.

В `.env.example` перечислены переменные для Kafka PLAINTEXT/SSL/SASL.
После заполнения конфигурации и подготовки реальных весов:

```powershell
docker compose up -d --build advisor
```

Compose использует постоянный `advisor-state`, не создаёт Kafka и не запускает
MinIO без отдельного явно выбранного local-профиля. В Kafka-режиме используется
`configs/checklist-kafka.json` с 12 категориями. Автоматическое подтверждение
выключено существующим `configs/calibration.json` до доменной валидации.
Модель настоящая, но точность новых prompts/категорий пока не измерена.

Проверка 02.11.2026: изолированный тест настоящих Kafka/MinIO/Advisor и рестарта
проходит; воспроизведение — `scripts/kafka_e2e.py`, результаты — `VERIFICATION.md`.
Контракт входного Kafka JSON: `contracts/photo-event.schema.json`. Непригодные по
качеству снимки без подтверждения категории требуют `needs_review`; поле photos
также содержит quality, quality_issues и duplicate_of. Ревизии принимаются строго
целыми числами. ETag со `*` или списком значений запрещён; S3 null version без ETag
не считается неизменяемой ссылкой. Калибровка связана с policy_version=photo-advisor-v2.

Обучаемый backend (03.11.2026) выбирается `CV_BACKEND=trained`. Он добавляет в photo
поля `score` и `score_kind=softmax`. Это оценка модели, не измеренная вероятность;
`confidence` остаётся null. `similarity` применима к прежнему CLIP и не заменяет score.
Рабочий допуск обученных весов отдельно защищён проверкой артефакта и статистики.
При ручной правке `category` содержит выбранную пользователем категорию, а `candidate`
сохраняет исходного кандидата CV; score относится к этому кандидату, не к ручной метке.
Текущие обученные веса экспериментальные; автоматическое подтверждение выключено.
